# 平台场景覆盖与智能化架构说明

> 更新日期：2026-07-21 | 本次升级主题：**多格式文档能力 + 专业对账引擎 + LLM 智能化场景覆盖**

---

## 一、设计哲学：LLM 负责"理解"，代码负责"红线"

实际审计工作中的场景千变万化：台账有明细级的、按年汇总的、分类汇总的；匹配有全量的、也有"提取流水中医保回款再核对"的部分提取式；表头更是千奇百怪（` 摘要` 带空格、`借方（支取）` 带括号、`兹收/兹付` 自造词）。

面对这种多样性，平台的分工是：

| 层 | 职责 | 为什么 |
|---|---|---|
| **LLM（qwen3-235b）** | 场景理解、列语义兜底映射、DAG 规划编排、报告措辞 | 规则不可能穷举现实世界的表头与业务形态；235B 的智能是场景覆盖面的杠杆 |
| **语义注册表**（`core/column_semantics.py`） | 列名→业务语义角色（可扩充的单一事实来源） | 消除散落在各模块的硬编码列名 |
| **场景知识包**（`config/scenario_packs.py`） | 场景以数据注册：规划检查单、必需算子、交付物、容差纪律 | 新场景加配置不加引擎；RAG 知识从"参考资料"升级为"规划约束" |
| **确定性引擎** | 方向镜像、±0.01 精确、勾稽、MUS、幻觉熔断、不编造数据 | 专业红线绝不能交给概率模型 |

**一句话：让 LLM 在"真实列名 + 语义候选 + 场景检查单"的约束下做规划，而不是让它在真空里猜。**

## 二、多格式文档能力（已达能力清单"跨文档比对"要求）

`core/document_loader.py` 统一加载：

| 格式 | 文本 | 表格 | 备注 |
|---|---|---|---|
| xlsx/xls/csv | — | ✅（自动表头检测/编码容错） | 原有 |
| docx | ✅ 段落 | ✅ 全部内嵌表格→DataFrame | python-docx |
| doc | ✅ | ✅ | 经 Word COM 转 docx（需本机装 Word），否则明确报错 |
| pdf | ✅ PyMuPDF | ✅ pdfplumber | 扫描件提示需 OCR |
| md | ✅ | ✅ pipe 表格解析 | LLM 生成底稿常见 |
| txt | ✅ | — | chardet 编码探测 |

接入点：上传白名单（`.pdf/.md/.txt` 新增）→ chaos_input 嗅探（文档预览+内嵌表格列入 Catalog）→ data_sniffer → Load 算子（沙箱内 `_load_any_document` 兜底）→ 匹配/对账引擎（文档表格与 Excel 同权）。沙箱镜像 Dockerfile 已补 `python-docx/PyMuPDF/pdfplumber/chardet/rapidfuzz`（需 `docker build` 重建生效；平台层物化路径不依赖镜像）。

## 三、专业银行对账引擎（`core/bank_reconcile_engine.py`）

```
序时账/台账 × 银行流水
  → 类型识别（journal / bank_statement / generic_ledger 通用台账）
  → 列语义映射（规则优先，LLM 兜底，不臆造）
  → 方向镜像归一（账方 借−贷 / 流水 收入−支取；收支式台账自动判定口径）
  → 账户过滤（流水多账户 → 单账户）
  → 双方勾稽（期初+发生=期末）
  → 逐笔匹配 L1(精确+同日) → L2(精确+窗口±N天) → L3(n:m 拆分合并) → L4(模糊仅人工复核)
  → 未匹配分类：未达四分类（需期后验证）/ 默认待人工核查（禁止洗白）
  → 交付：逐笔对账明细底稿 + 银行存款余额调节表 + 未达/待核查清单 + 异常资金交易清单（12号文红旗）
```

红线：逐笔 ±0.01 元硬编码；利息/冲正单独成类不删除；兜底一律"待人工核查"。

## 四、场景覆盖矩阵（`config/scenario_packs.py`，可纯配置扩充）

| 场景 | 触发线索 | 规划约束（检查单注入 LLM） | 确定性引擎 |
|---|---|---|---|
| 明细级逐笔对账 | 对账/核对/相符/序时账 | 账户过滤→方向镜像→勾稽→L1~L4→未达四分类→调节表 | bank_reconcile_engine（快车道） |
| 汇总级勾稽（年度/分类汇总台账） | 汇总/总额/按年/按类别 | 同维度 GroupBy→键对齐→三类差异列示→容差用户指定 | 通用算子（LLM 编排） |
| 提取式部分金额匹配（医保回款式） | 提取/筛选/医保/回款 | 提取规则写进 pattern+留痕→汇总比对→未提取部分单列 | matching_engine |
| 大额交易筛查 | 大额/超过/筛查 | 阈值条件化+降序+红旗特征 | 通用算子 |
| 单表分析 | 筛选/汇总/透视 | 单表路由，不虚构第二表 | single_table_filter |
| 函证 | 函证/询证 | 积极式默认+未回函替代程序+差异登记 | audit_procedures |
| 审计抽样 | 抽样/抽凭 | MUS 间隔+随机起点+种子可复现+tainting 评价 | audit_sampling（CSA 1314） |
| 穿行测试 | 穿行/流程/断点 | 节点按业务实际，不得只看日期/金额/状态 | 通用算子 |
| 报告/底稿生成 | 报告/底稿/出具 | 数字与审定数同源勾稽 | template_engine |
| 跨文档比对 | 文档/docx/pdf/两份 | 文档表格与 Excel 同权 | document_loader |

**明细/汇总自动分流**：快车道只承接明细级台账（有逐笔日期+足够行数）；汇总级数据自动交 LLM 按 `summary_compare` 场景规划（GroupBy→Merge→Diff）。

## 五、让 LLM 更聪明的四个机制

1. **结构化感知**：编译 prompt 中的 Data Catalog 现在携带——真实列名(dtype)、语义角色（date→日期， debit→借方金额…）、无意义键黑名单（序号/编号禁止连接）、跨表连接键建议（`客户名称↔对方客户名称`）、文档文本预览。LLM 不再需要猜列名。
2. **场景检查单即规划约束**：命中场景后，该场景的专业步骤清单注入 prompt（如银行对账六步），且 DAG 校验器强制必需算子存在（缺 Reconcile 自动补）；硬约束写明"source_file 与列名必须逐字来自 Catalog"——从机制上消灭幻觉文件名（此前 `DAGParser.parse` 未传 known_files，已修复并接 rule_fix 熔断）。
3. **LLM 兜底语义映射**：异形表头（`兹收/兹付/划拨日期`）规则不中时，把真实列名+样例行交 vLLM 映射为语义角色，结果入 Catalog 供确认；离线则宁缺毋滥。
4. **教原理的 few-shot**：新增"序时账×流水逐笔对账"范例（方向镜像+精确到分+待核查兜底），噪声示例中的"利息"已移除（单独成类），逐笔示例容差统一 `tolerance_abs=0.01`。

## 六、本次修复的关键缺陷（对照审查报告）

- B1/B2：Merge 真 `left_on/right_on` 映射 + 真 `date_window_days`（日期对 equi-join+窗口过滤）；无意义键拒绝合并（"按序号对账"终结）
- B3：Diff 改 outer merge + indicator 三态 + `tolerance_abs/tolerance_pct` 真实生效
- B4：Reconcile / AuditAdjustment 算子实现（不再"合法但不存在"）
- B5：`_block_candidates` 分桶恒等 bug + `{key-1: key+1}` 字典 bug + 500×500 静默截断（改告警+上限内全量）
- B7：算子补全硬编码列名 → 运行时 auto 解析
- B8：ffill 数据伪造层删除 → 《数据缺失清单》（缺失只标记，不编造）
- C1：`DAGParser.parse` 两处补传 `known_files` + rule_fix 熔断（幻觉拦截）
- C4：对账槽位专业化（账户/期间/数据键）；抽样必问方法
- 数据流：`input_from → params.depends_on` 接线（Merge/Diff/Reconcile 不再"猜最后两个变量"）
- `_fuzzy_match_name` 行政区划清洗限定医保场景（防"朝阳区/海淀区甲公司"张冠李戴）
- 生成代码 stdout UTF-8 重配置（GBK 控制台不再因 ⚠/❌ 崩溃）
